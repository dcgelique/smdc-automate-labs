Lab 109:40–10:30Excel + filtering

Process and analyse ticket data

Goal: Read the supplied synthetic ticket export and identify records requiring attention.

  1. Confirm the workbook data is formatted as a table named Tickets.
  2. Create an instant cloud flow for workshop testing.
  3. Add List rows present in a table.
  4. Add filters for Open, Resolved, Critical, SLA Breached, Reopened, Unassigned, and Aging tickets.
  5. Use length() to count each result set.
  6. Inspect the source rows and calculated counts in run history.

Detailed build steps

  1. In Power Automate, select Create and create an Instant cloud flow. Name it AM - Service Operations Insights and choose Manually trigger a flow.
  2. Select New step, search for Excel Online (Business), and add List rows present in a table.
  3. For Location, choose the OneDrive or SharePoint location containing the starter workbook. Select the document library, browse to the workbook, then choose table Tickets.
  4. Select Save, then Test → Manually → Run flow. Open the successful run and expand List rows present in a table. Confirm the output contains the expected ticket rows.
  5. Add a Filter array named Filter - Open Tickets. In From, choose the value output from Excel. Configure the rule so Status equals Open. Repeat for Resolved, Critical, SLA Breached, Reopened, and Unassigned using the matching workbook fields.
  6. Add a Compose action named Count - Open. In Expression, enter length(body('Filter_-_Open_Tickets')). Repeat the pattern for each filter, selecting the exact generated action names in your flow.
  7. For Aging, use the workshop field or threshold supplied by the facilitator. Do not create a new SLA rule that is not present in the lab instructions.
  8. Save and run the flow again. Expand each Filter array and Compose action and compare the results with the source workbook before continuing.
Troubleshooting: If Excel does not show the table, confirm the workbook is stored in OneDrive/SharePoint and the source range is formatted as an Excel table. If an expression references a renamed action, reinsert the action output or update the expression.

Lab 210:45–11:30Variables + expressions

Generate operational insights

Goal: Turn the validated results into a concise operational summary.

  1. Reuse the counts from Lab 1.
  2. Calculate total, open, resolved, Critical, breached, reopened, and aging metrics.
  3. Use the facilitator-supported category-count pattern to identify the highest-frequency category.
  4. Create a plain-language summary using Compose.
  5. Compare every statement with the source workbook.

Detailed build steps

  1. Open the working AM flow from Lab 1 and select Save as if the facilitator asks you to preserve a checkpoint copy.
  2. Add a Compose action named Insight - Total Tickets and use length(outputs('List_rows_present_in_a_table')?['body/value']), or select the appropriate Excel output and use the expression editor.
  3. Reuse the count Compose outputs created in Lab 1 for Open, Resolved, Critical, SLA Breached, Reopened, and Aging.
  4. For category frequency, follow the facilitator-supported pattern: filter the ticket array once for each workshop category, calculate each category count with length(), then compare the counts using the supplied lab logic.
  5. Add a final Compose named Operational Summary. Insert static labels and dynamic outputs so the text contains the reporting period and each validated metric.
  6. Keep the wording factual. Example: Critical tickets: 4. Do not change the wording to Security failures caused four critical tickets unless the dataset explicitly establishes that conclusion.
  7. Select Save and run another manual test. Compare every number and the top category with the workbook.
  8. Open Run history, select the test run, and inspect the final Compose output. Correct any mismatch before Lab 3.
Checkpoint: The flow must produce the same answer every time it runs against the unchanged starter workbook.

Lab 311:30–12:15Alerts + recurrence + HTML

Automate alerts and weekly reporting

Goal: Finish one end-to-end morning solution.

  1. Add a condition for Critical, breached, or unassigned high-priority tickets.
  2. Send an urgent workshop notification when exceptions exist.
  3. Create an HTML weekly service summary from the Lab 2 metrics.
  4. Add a weekly recurrence trigger or save a scheduled version of the flow.
  5. Send the report to the controlled workshop destination.
  6. Optionally write the reporting result to a Report Log list.

Detailed build steps

  1. In the AM flow, add a Condition after the calculations. Build the urgent rule from the validated exception counts, for example: Critical count is greater than 0 OR SLA Breached count is greater than 0.
  2. In the True branch, add Office 365 Outlook - Send an email (V2) or the facilitator-approved Teams action. Address it only to the workshop destination.
  3. Set the subject to a clear workshop label such as Workshop Service Operations Alert. In the body, insert the Critical, SLA Breached, Unassigned, and Aging counts plus the reporting period.
  4. In the False branch, add a simple Compose named No urgent exceptions. This makes the non-alert path visible in run history.
  5. Create the weekly version: from My flows, choose New flow → Scheduled cloud flow. Set the workshop recurrence, then reproduce or reuse the validated ticket-processing steps as instructed by the facilitator.
  6. Add Send an email (V2). Build an HTML body with headings for Service Summary and Exceptions. Insert the Lab 2 metrics as dynamic content. Keep the message concise and factual.
  7. Select Save. Use Test for the manual/instant version and, for the scheduled version, use the designer test options available in the workshop environment.
  8. Verify the delivered message and compare every metric against the source workbook.
Important: Use controlled workshop recipients. Do not send synthetic incident alerts to operational distribution lists.

Lab 413:20–14:10SharePoint + approvals

Build the review and approval workflow

Goal: Create a durable human-in-the-loop review process.

  1. Trigger when a Policy Review record is set to Submitted.
  2. Retrieve the reviewer and document link.
  3. Add Start and wait for an approval.
  4. Include the Policy/Process ID, title, owner, due date, and document link.
  5. Create Approved, Rejected, and Revision Required outcomes.
  6. Store outcome, reviewer, comments, decision date, and status.
  7. Notify the process owner.
  8. Prevent update loops using status checks or a trigger condition.

Detailed build steps

  1. Open the supplied Policy Reviews list and confirm the test record contains a reviewer, status, due date, and document reference.
  2. In Power Automate, select Create → Automated cloud flow. Name it PM - Policy Review and choose the SharePoint trigger When an item is created or modified (or the facilitator-specified list trigger).
  3. Select the workshop Site Address and List Name. Add a status check immediately after the trigger so the approval path only continues when Status equals Submitted.
  4. Add Start and wait for an approval. Choose the workshop approval type. Set Title using the Policy/Process ID and title, and set Assigned to from Reviewer Email.
  5. In Details, insert the process owner, due date, review cycle, and the synthetic document link. Make the request clear enough that an approver can decide without guessing what is being reviewed.
  6. Add a Condition based on the approval outcome. For the basic workshop version, map Approve vs Reject first. To demonstrate Revision Required, use the facilitator-provided outcome/status pattern or a follow-up status field.
  7. In each path, use Update item to save Status, reviewer, decision date, comments, and outcome. Then add Send an email (V2) to notify the process owner.
  8. Select Save and Test. Submit a synthetic record, respond from email or the Power Automate approvals center, and inspect run history after the response is submitted.
Tip: Approval requests can be responded to from email, the Power Automate approvals center, or the Power Automate app. Keep your workshop approver account signed in.

Lab 514:10–14:50State + routing

Handle revision, resubmission, and rerouting

Goal: Continue the review process without losing business history.

  1. Select a Revision Required record.
  2. Update the synthetic document while preserving its Policy/Process ID.
  3. Increment Review Cycle.
  4. Set the status to Resubmitted.
  5. Use explicit Review Route or Affected Reviewer data to select the reviewer.
  6. Start the next approval cycle.
  7. Preserve prior comments and decisions in a history field or history list.

Detailed build steps

  1. Use the supplied record whose Status is Revision Required. Note the current Policy/Process ID, Review Cycle, reviewer comments, and document link before making changes.
  2. Update the synthetic document in the workshop library. Follow the facilitator’s document-version approach; do not delete the prior business record.
  3. In the review flow, add or extend the branch for Revision Required. Use Update item to set the workflow state required for resubmission while retaining the original Policy/Process ID.
  4. Increment Review Cycle using the current value plus 1. If your column is numeric, use the expression pattern add(int(...),1) with the Review Cycle dynamic value supplied by the trigger or Get item action.
  5. Read Review Route or Affected Reviewer from the list. Use a Switch or Condition only if the starter data contains more than one explicit routing path.
  6. Add the next Start and wait for an approval action and assign it to the reviewer from routing data. Include the new Review Cycle and the prior reviewer comments in the approval details.
  7. Preserve history using the facilitator-supported approach: append to a Review History text field or create a row/item in the supplied history structure before overwriting current-state fields.
  8. Resubmit and test. Confirm the new reviewer receives the request and the prior decision remains visible in the history.
Boundary: The flow follows explicit routing data. It does not read the revised document and infer which approvers need to re-review it.

Lab 615:05–15:50Schedule + error handling

Automate reminders, escalation, and exception handling

Goal: Make the afternoon solution supportable and resistant to duplicate follow-up.

  1. Create a scheduled flow for Submitted, In Review, and Revision Required records.
  2. Calculate days until or after Due Date.
  3. Send a due-soon reminder to the reviewer.
  4. Escalate overdue items to the reviewer and process owner.
  5. Update Last Reminder Date and Reminder Count.
  6. Skip records already reminded today.
  7. Add Try, Catch, and Finally scopes.
  8. Log the flow name, record ID, stage, safe error summary, and run URL.
  9. Force one controlled failure and verify the exception path.

Detailed build steps

  1. Create a new Scheduled cloud flow named PM - Review Follow-up. Set it to the workshop recurrence provided by the facilitator.
  2. Add SharePoint Get items for the Policy Reviews list. Use the workshop list as the authoritative source for Status, Due Date, Last Reminder Date, Reminder Count, reviewer, and process owner.
  3. Add Apply to each over the returned records. Inside the loop, first skip states that should not be followed up, such as Approved or Rejected.
  4. Add the due-date logic supplied in the lab: Future → no action, Due Soon → reviewer reminder, Overdue → reviewer plus process-owner escalation.
  5. Before sending, check Last Reminder Date. If it already equals the current workshop date, skip sending. This prevents duplicate same-day reminders.
  6. After a successful reminder, use Update item to set Last Reminder Date and increment Reminder Count.
  7. For error handling, add three Scope actions named Try, Catch, and Finally. Move the main retrieval/decision/notification work into Try.
  8. On Catch, use Configure run after so Catch runs when Try has failed, timed out, or been skipped. Add the facilitator-provided exception-log action and record Flow Name, Business Record ID, Stage, safe Error Summary, and Run URL.
  9. Configure Finally to run after both Try success and Catch completion, then update a final processing-status field or visible lab marker.
  10. Force one controlled failure, such as temporarily using an invalid workshop notification destination only if the facilitator instructs you to do so. Confirm Catch executes and the exception is logged, then restore the correct configuration.
Troubleshooting: When a run fails, open Run history and inspect the first failed action. Fix the source issue rather than adding extra retry logic without understanding the failure.
